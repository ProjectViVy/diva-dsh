# dsh-live2d —— 角色舞台的遥控器

这个插件现在只做一件事：把对话里的 `l2d_*` 工具调用**转给独立舞台进程**。

角色本身（渲染、模型、编译器、引擎、指令箱、认证）已经搬进仓库根目录的
[`stage-app/`](../../stage-app/)，它是一个独立进程：自己的端口、自己的令牌、
自己的生命周期。DSH 重启不影响它，它挂了也不影响 DSH。

## 为什么变成这样

原来角色舞台住在设置面板里：宿主托管页面与素材，自己造一套鉴权，浏览器长轮询取活。
结果是**呈现与具身被焊进了宿主的构建**，代价在真机上暴露了两次：

- 回执发不出去，任务停在「已取走」，查不到原因——因为这条路被宿主的鉴权与文档模型包着；
- 宿主重启后页面不重挂舞台，用户必须手动刷新。

这不是实现细节的问题，是边界的问题。研究包里对 Mirror 的定义说得很直接：

> Mirror 是 DIVA 的可替换呈现与具身前端。
> VRM/Live2D 渲染、模型和动画资产应当逐步迁出 Core，通过稳定合同运行，
> 而不是成为 Core 或主 GUI 无法移除的编译耦合。

所以这次分离不是「试不动了换方案」，是回到原本该有的位置。

## 现在的边界

| 层 | 负责 | 不负责 |
|---|---|---|
| **舞台**（`stage-app/`） | 渲染、模型、编译器、引擎、指令箱、令牌、审计 | 知道 DSH 存在 |
| **本插件**（两个文件） | 转发工具调用、把失败翻译成人话 | 编译、渲染、存模型、鉴权 |
| **DSH** | 提供 tools 服务 | 托管舞台 |

## 工具

| 工具 | 作用 |
|---|---|
| `l2d_capabilities` | 读角色能力与硬规矩（编排前先看） |
| `l2d_catalog` | 列真实存在的表情/动作/手势名（别编名字） |
| `l2d_compile` | 只校验不演，先试再演 |
| `l2d_execute` | 交给舞台演，返回 jobId |
| `l2d_state` | 追进度，`progress=1` 才算演完 |
| `l2d_stop` | 平滑回待机 |

## 跑起来

```bash
# 1. 独立舞台（另开一个终端：这个进程不跟 DSH 一起生灭）
npm --prefix stage-app start

# 2. 按它打印的地址打开页面（带令牌）
#    http://127.0.0.1:5462/?token=…

# 3. 舞台没反应时先自检
npm --prefix stage-app run check
```

舞台启动时把令牌写到 `$DSH_HOME/live2d/stage-token`（权限 0600），插件从这里读——
两边都从 `$DSH_HOME` 推导，不各写一份。

## 舞台没在跑的时候

工具会直接说「舞台没有运行」，不会偷偷退化成一套内嵌实现。
宁可明确地少一个能力，也不要两套东西各说各话。

## 来源与许可

本仓库原为 `dsh-superagent-template` 工作区中的一个模块，现拆出来独立建仓维护。

- **来源**：本项目原创。这里只有把 `l2d_*` 工具调用转给独立舞台进程的桥，
  不含渲染层、界面与模型资产。
- **相关**：舞台本体在 `stage-app`；Live2D Cubism Core 的加载方式与授权注意事项见那里的
  [`vendor/README.md`](../../stage-app/vendor/README.md)。
