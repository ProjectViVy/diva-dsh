# PENS 设计与接入：把「外部应用」变成 agent 可玩的动作面

- 状态：设计提案（**未写代码、未装依赖、未实测任何游戏**）
- 日期：2026-11-11 (Asia/Shanghai)
- 前置：[`workbench-landscape.md`](workbench-landscape.md) §10（无记忆、无人格、只接线的收窄结论）、`.workspace/pens/docs/DECISIONS.md`
- 驱动需求：**不带人格与记忆、只做外部功能接线；能接 Codex / Hermes；尽可能多地让 agent 玩游戏**
- 方法：先给结论，再给「最简方案 + 一个备选 + 依据」；不做需求外功能，不加没有测量支撑的机制

---

## 0. 结论（先看这 9 条）

1. **接口只开 4 个工具，且永远只有 4 个**：`pens_catalog` / `pens_attach` / `pens_observe` / `pens_act`。任何应用的动作集不注册成工具，而是走 **schema 资源按需拉取**。
   - 依据：淋雨家工作台的实测——Blender 32 工具 ≈ **8.9k token/轮**、桌面操控 57 工具 ≈ **26.8k token/轮**、5 个网页 AI 全开 ≈ **660/轮**（[§4.6](workbench-landscape.md)）。工具面随应用数量线性涨，schema 按需拉才是常数量级。
2. **「尽可能多地玩游戏」不是写 N 个适配器，而是写 5 个「接口族」适配器 + 每游戏一份声明式 profile**。游戏接入的成本项是「族数」，不是「游戏数」。
   - 一个 libretro/模拟器族适配器 ≈ 上千款老游戏；一个 CDP 浏览器族 ≈ 全部网页游戏；一个 BepInEx/SMAPI 族 ≈ 大量 PC 单机；一个 UIA 族 ≈ 棋牌/经营类客户端；一个像素底座 ≈ 理论上全部（兜底但最贵）。
3. **把「能玩多深」做成显式分级 D0–D3**（旁观 / 有限操作 / 能玩完一局 / 能跨会话续局），每款游戏在能力账本里记自己的深度。**不承诺「都能玩」，只承诺「每款游戏都知道自己到哪一档」**——这是「尽可能多」的诚实表达。
4. **观察必须可压缩**：每轮只发「结构化摘要 + 变化增量」，帧与裁剪区按需拉。游戏是高清帧的重灾区，不做这件事，「多」会直接死在 token 上。
5. **时间模型是游戏与工具的分水岭**：回合制由 agent 驱动；实时由 PENS 驱动时钟，agent 的动作进队列并按声明的时间预算降级（合法暂停 / 合帧 / 判「不适合」）。
6. **状态归应用、进度归 agent、暴露权归宿主**（承接 §10.2）：PENS 只持句柄与租约，不存「上次玩到第几关」；能看什么由宿主决定。
7. **传输用 MCP，语义用 PEN**：MCP 是线，PEN 是插头。自定义 SDK 会立刻退化成「每个 host 一个适配器」，这是跨 agent 需求的反面。
8. **首版只做一条链**：模拟器族 + 3 份 profile + 4 工具 + 租约/权限账本骨架。不做商店、不做反作弊绕过、不做联网竞技。**桌面壳要做，但排在 M1**（外挂式：托盘 + 悬浮 HUD，见 §16）。
9. **游戏接入有红线**：单机/离线优先；联网竞技默认拒接（反作弊与 ToS），需要显式白名单 + 人审。多不等于无差别。

## 1. 口径与边界

| 项 | 定义 |
| --- | --- |
| 「接一个游戏」算什么 | 能**看到**该游戏的结构化状态、能**执行**该游戏声明的动作、能**停下**且状态不被破坏、能**查清**失败原因。四项缺一不算接上 |
| 「能玩」算什么 | 至少 D1（有限操作）；「玩完一局」= D2；「下次接着玩」= D3 |
| 不做什么 | 不做游戏里的 AI（那是 agent 的事）、不做匹配/排行/社交、不做反作弊、不做游戏本体分发 |

三条不变量（与 §10.3 一致）：

1. PENS 持久化只允许 **句柄 / 权限账本 / 包元数据**；
2. PENS 不做「无人请求的主动唤醒」（MCP 是拉取模型），需要定时就由宿主自己的 job 驱动；
3. PENS 不理解语义——不理解「这关难不难」「这步好不好」，只保证看得到、动得了、停得下、查得清。

## 2. 总体架构

```text
        Codex        Hermes        DSH/Superagent        （任意 host，各自有人格/记忆）
           │            │                │
           └────────────┴────────────────┘
                        │  MCP（4 个恒定工具 + schema 资源 + 进度通知）
                        ▼
┌───────────────────────────────────────────────────────────────┐
│                       PENS 总线（无记忆）                      │
│  catalog（能力账本） · attach（会话/租约） · observe · act      │
│  作业与时钟 · 权限校验 · 制品（路径+校验和） · 错误语义         │
└───────────────────────────────────────────────────────────────┘
                        │  5 个「接口族」适配器（代码）
      ┌─────────────────┼──────────────┬─────────────┬──────────┐
      ▼                 ▼              ▼             ▼          ▼
  libretro/模拟器    CDP/浏览器     Mod 框架       UIA/AXTree   像素底座
  （RAM + 输入）    （DOM + JS）  （BepInEx/SMAPI）（控件树）  （截图+键鼠）
      │                 │              │             │          │
      └─────────────────┴──────────────┴─────────────┴──────────┘
                        │  每游戏一份 profile（声明式数据）
                        ▼
                 真实游戏（状态与存档归它自己）
```

三个平面、一个账本：

| 平面 | 内容 | 形态 |
| --- | --- | --- |
| 清单平面 | `catalog`：装了什么、每款到哪一档、需要什么权限 | 账本（可导出 JSON） |
| 总线平面 | 会话、租约、时钟、作业、观察压缩、错误语义 | 常驻服务（单进程） |
| 适配器平面 | 5 个族适配器，每族一个 | 代码，量大且互斥 |
| 声明 | 每游戏一份 `profile.yaml` | 数据，边际成本接近零 |

## 3. 核心接口：4 个工具 + 按需 schema

```text
pens_catalog()
  → { apps: [ { id, kind, depth: D0..D3, status: installed|running|idle,
               actions: <schema 摘要，仅计数>, observe: [summary|frame|region],
               timing: turn|realtime(tick_ms), permissions: [...], version } ] }

pens_attach(app_id, mode: play|spectate, agent_id, session_id)
  → { lease_id, expires_at, schema_uri: "pens://schema/<app_id>",
      state: <首帧摘要>, capabilities: <该 app × 该 host 的已验证项> }

pens_observe(lease_id, want: summary|frame|region(box), since: <cursor>)
  → { cursor, summary: {...}, delta: {...}, frame?: <ref>, tick?: n }

pens_act(lease_id, action, args, expect?: <predicate>, timeout_ms)
  → { ok, applied, observed_after: <摘要/ delta>, job?: { id, progress } , error?: <code> }
```

四条设计约束（每条都有实测依据）：

1. **工具数量恒定**：不按应用注册工具。Blender 那 32 个工具、桌面操控 57 个工具的做法，在「尽可能多」的场景下会让每轮 context 爆炸。**动作集走 `schema_uri` 资源，按需拉、可缓存、可裁剪**。
2. **`act` 自带 `expect`（读回自证）**：动作后由适配器读回状态断言（`expect` 不满足即 `ok:false` 并附差异），把「点了 ≠ 生效」挡在总线里，而不是让 agent 靠猜。
3. **长动作一律返回 `job`**：渲染、加载、过场、下载更新都是分钟级；调用立即返回 job id，进度走通知，取消走 `pens_act {action: cancel}`。
4. **观察带游标**：`since` 让 host 只说「我上次看到哪」，总线只发增量；重复帧不发（hash 相同则 `frame` 缺省）。

## 4. 五族适配器：覆盖杠杆在这里

| 族 | 接口落点 | 覆盖量级 | 单轮成本 | 深度上限 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| **A 模拟器（libretro / BizHawk）** | 内存读（`retro_get_memory_data` / Lua API）+ 输入注入；帧缓冲可取 | **上千款**（NES/SNES/GBA/PS1/N64/GB…） | 极低（结构化数值，几十–几百 token） | D3 | 存档格式、金手指边界、不同核心内存映射 |
| **B 浏览器（CDP）** | `Runtime.evaluate` + DOM 读取 + 合成输入 | 所有网页/Electron 游戏 | 低（DOM 文本/数值） | D2–D3 | 自绘 canvas 游戏读不到 DOM（退化为像素） |
| **C Mod 框架（BepInEx / SMAPI / Fabric）** | 进程内插件：读写游戏对象、发指令 | PC 单机「数十–数百款」 | 低 | D3 | 每款仍要一个薄插件；版本绑定强 |
| **D UIA / 控件树** | Windows UIA / macOS AX | 棋牌、经营、卡牌客户端 | 中（控件树可裁剪） | D2 | 自绘界面读不到控件 |
| **E 像素底座（截图 + 键鼠）** | 屏幕捕获 + 输入合成（+ 可选视觉模型兜底） | **理论上全部** | 高（每帧 1–2k token，含视觉） | D1–D2 | 慢、脆、贵；只做兜底 |

**关键判断**：E 覆盖最广但最贵，A 覆盖极广且极便宜，B 在网页游戏上几乎免费。所以顺序不是「先做最难的」，而是：

> **先做 A 与 B（便宜且覆盖大），E 只做「能看能停」的兜底，C/D 按需增量。**

一个可计算的覆盖公式（用来回答「尽可能多」到底多到哪）：

```
可玩游戏数 ≈ Σ_族 (该族覆盖款数) × P(该款有 profile) × P(该 host 支持该深度)
```

真正能推高这个数的动作，按性价比排序：

1. 增加**族**（+1 族 ≈ +一个数量级的游戏）；
2. 提高单族的 **profile 覆盖率**（每份 profile ≈ 1–30 分钟工作量，纯数据）；
3. 提高缺口处的**像素兜底质量**（只影响「能看」，不影响「能玩完」）；
4. 单个游戏做深度优化（最贵，最后做）。

## 5. 深度分级：D0–D3

| 深度 | 名字 | 能做什么 | 谁需要 | 判据 |
| --- | --- | --- | --- | --- |
| **D0** | 旁观 | observe only，能看画面/状态与日志 | 一切需要「看」的场景（陪看、复盘、解说） | 有帧或摘要，无需输入权限 |
| **D1** | 有限操作 | 固定动作集（走/跳/攻击/确认/暂停） | 「能动一下」的采样与演示 | 动作集封闭，失败可恢复 |
| **D2** | 能玩完一局 | 完整动作集 + 会谈对话/菜单/结算 | 真正的「玩」 | 连续 10 分钟无人工干预完成一局 |
| **D3** | 跨会话续局 | 存档读写 + 恢复 + 多局 | 长期陪玩、跨会话 | 断开重连后能在同一存档继续 |

账本里每款游戏一行：`{app, depth, host_support: {codex: D2, hermes: D1}, last_verified}`。**「尽可能多」= 让 D0 的款数最大化、D2 的款数尽量多、并诚实标注 D3 的缺口**。

## 6. 时间模型（游戏特有的、也是工具没有的）

| 类型 | 时钟由谁驱动 | `observe` 语义 | 动作策略 | 不适配时的降级 |
| --- | --- | --- | --- | --- |
| **回合制 / 慢节奏**（RPG、策略、卡牌） | agent | 每次 act 后返回新局面 | 同步执行 | 无 |
| **实时的可暂停**（模拟经营、可暂停的单机） | 双方 | 快照 + 短暂停 | 动作排队，超时自动暂停 | D2 降 D1 |
| **实时不可暂停**（动作、竞技） | PENS | 定时快照（`tick_ms` 声明） | 动作仅保留最新（合帧，不积压） | **判「不适合」，只给 D0 旁观** |
| **纯离线批处理**（回放、录像分析） | 无 | 一次性给终局 | 不允许 | 只读 |

三条硬规则：

1. **合帧不积压**：实时游戏里 agent 决策慢，就丢弃中间动作，只执行最新一条——积压的动作在游戏里等于「乱按」，比不按更糟。
2. **超时即停**：`act` 的 `timeout_ms` 到点必须能停（暂停/回到菜单/释放输入），不允许「卡在过场里」。
3. **不可暂停的实时游戏默认只给 D0**：这是对「尽可能多」的诚实约束——给不了公平的操作延迟，就不承诺能玩。

## 7. 观察压缩（「多」的经济学）

三档观察 + 一道 delta：

| 档 | 内容 | 典型成本 | 什么时候用 |
| --- | --- | --- | --- |
| `summary` | 结构化数值/对象表（血量、金钱、地图格、手牌） | 几十–几百 token | 默认 |
| `region` | 指定矩形裁剪帧（小地图、血条、对话框） | 数百 token | 需要看但不需要整屏 |
| `frame` | 整帧 | 1–2k token | 视觉兜底 / 新场景首次 |

配套机制：

- **delta**：只发「新增/变化」的字段与对象，`since` 游标对齐；
- **帧去重**：帧 hash 未变则不发（回合制里常见「画面没动」）；
- **自适应档位**：profile 里声明「默认 summary，每 N 回合补一帧」，由总线执行，agent 不必自己管；
- **预算护栏**：`observe` 可带 `budget_tokens`，超了总线自动降档——把成本控制放在总线，而不是每个 host 各写一遍。

依据：Blender/桌面操控的 token 实测（§4.6）说明「暴露即成本」；游戏每轮都观察，成本会乘上回合数，因此压缩不是优化，是可用性前提。

## 8. 接入协议（host 视角）

### 8.1 身份与租约

```
identity = (agent_id, session_id)
lease    = (lease_id, app_id, mode: play|spectate, depth, expires_at)
```

- `agent_id` 由宿主自报 + 首次接入时登记（无凭据 = 无记忆，也不假装有）；
- `spectate` 是只读租约：不抢玩家输入，可多 agent 同时旁观（直播式陪看）；
- `play` 是独占租约：同一 app 同一时刻只有一个 play 租约，其余排队或旁观；
- 续租/让出都是一次 `attach`/`act`，不做后台心跳（保持「无主动唤醒」）。

### 8.2 权限

四级：`(agent × app × action_class × depth)`。`action_class` 由 profile 声明（`input` / `menu` / `save` / `settings` / `network`），其中：

- `network` 默认拒绝（联网游戏）；
- `save` 需要显式授权（写存档 = 改用户数据）；
- `settings` 需要人审（改分辨率/音量会污染用户环境）。

### 8.3 错误语义（宿主可据此降级）

| 码 | 含义 | 宿主该做什么 |
| --- | --- | --- |
| `not_installed` | 没有该 app 的 profile | 提示安装/换游戏 |
| `not_running` | 进程没起 | 重试一次 attach |
| `version_mismatch` | 游戏/适配器版本不匹配 | 换版本或降档 |
| `denied` | 权限不允许 | 请求授权或降档 |
| `unsupported_capability` | 该 host 不支持该深度 | 降档（D2→D1/D0） |
| `timeout` / `crashed` | 超时、崩溃 | 停、释放租约、报制品（崩溃日志/存档副本） |

### 8.4 制品

存档、回放、截图、日志一律 **路径 + sha256**，由宿主决定存哪、要不要进自己的记忆。PENS 不复制、不索引、不推理。

## 9. 每游戏一份 profile（声明式，边际成本近零）

```yaml
# profiles/stardew-like.yaml（示意，非真实游戏）
id: stardew-like
kind: mod            # a=libretro | b=cdp | c=mod | d=uia | e=pixel
launch:
  cmd: "StardewModdingAPI.exe"
  cwd: "D:/Games/Stardew"
  attach: { type: ipc, port: 7878, ready_probe: "state.ready==true" }
timing: { mode: turn, max_turn_ms: 30000 }
observe:
  default: summary
  summary: { hp: "player.health", money: "player.money", time: "clock", inventory: "player.items[]" }
  region: { box: [0, 0, 320, 180], label: minimap }
  every_n_turns_frame: 5
actions:
  move:   { args: {dir: enum[n,s,e,w]}, class: input, pre: "!state.paused" }
  use:    { args: {slot: int 0..11},    class: input }
  talk:   { args: {target: id},         class: menu }
  sleep:  { args: {},                   class: menu, expect: "state.day == prev.day + 1" }
  save:   { args: {slot: int},          class: save }
depth: D3
limits: { max_actions_per_turn: 1, forbid: [network] }
```

要点：

- **`expect` 写在 profile 里**，不是写给 agent 的提示词——读回自证属于适配器；
- **`class` 决定权限**，不由 agent 声明；
- **`depth` 是实测值**，由「连续 10 分钟完成一局」这类验收刷新，不是写死的美好愿望；
- 一份 profile 通常 **20–60 行**，就像给工作台加一个场景 JSON。

## 10. 分期（最小可用，MFBE 顺序）

| 期 | 范围 | 验收（可跑、可测） | 估工 |
| --- | --- | --- | --- |
| **M0** | 4 工具 + **A 族（libretro）** + 3 份 profile（1 回合制 RPG / 1 平台跳跃 / 1 策略）+ summary/delta + 租约 + 错误码 | 两个 host（Codex/Hermes）用同一 profile 各玩 10 分钟：RPG 到 D2、平台跳跃到 D1 且能停；每轮观察 ≤ 400 token | 1–2 周 |
| **M1** | **B 族（CDP）** + D0/D1 分级 + 观察预算护栏 + 能力账本导出 | 网页游戏 3 款到 D1；预算护栏生效（超限自动降档） | 2–3 周 |
| **M2** | **C 族（BepInEx/SMAPI）** + 存档/续局（D3）+ **E 族像素兜底**（D0） | 一款 PC 单机到 D3（断连重连继续）；任意游戏能 D0 旁观 | 3–5 周 |

明确不做（否则「多」会变成「散」）：商店/分发、反作弊、联网竞技、跨机器同步、排行榜。桌面壳不在 M0，在 M1（§16）。

## 11. 备选方案与取舍

| 方案 | 覆盖 | 每轮成本 | 跨 host | 结论 |
| --- | --- | --- | --- | --- |
| **A 每游戏一个 MCP server**（现状做法） | 低（写一个才有一个） | **高**（工具随应用线性涨：8.9k / 26.8k 实测） | 靠 MCP 天然通 | 否：token 税与版本漂移 |
| **B computer-use 一把梭** | 最高（所有屏幕） | 最高（26.8k + 每帧图像） | 通 | 只做 E 族兜底 |
| **C 本设计**（5 族 + profile + 4 工具恒定 + 深度分级） | 高（族级杠杆） | 低（摘要 + delta） | 通（MCP） | **推荐** |
| D 只接官方 bot/训练 API（如星际 2） | 极低 | 极低 | 通 | 作为 A 族的补充，不做主线 |

**最简方案 = C 的 M0**：一个族（A）、三个 profile、四个工具。**一个备选 = B**（只在需要「任何游戏都能看一眼」时启用）。**依据**：族级复用让边际成本接近零；工具面恒定避免 §4.6 实测的 token 线性膨胀。

## 12. 风险与红线

| # | 风险 | 级别 | 缓解 |
| --- | --- | --- | --- |
| G-1 | 反作弊 / ToS：联网游戏的自动化操作会被封号甚至违法 | **高** | 联网竞技默认 `denied`；白名单需人审 + 明示责任；只做单机/离线 |
| G-2 | 存档污染：agent 改坏用户存档 | 高 | 写存档前快照、副本落盘、可回滚；`save` 类动作需显式授权 |
| G-3 | 实时性不足被当成「能玩」 | 中 | 不可暂停的实时只给 D0；深度分级写进账本 |
| G-4 | 像素兜底的 token 爆炸 | 中 | 预算护栏 + 帧去重 + 默认 summary |
| G-5 | 版本漂移（模拟器核心、Mod 框架、游戏更新） | 中 | profile 里 pin 版本；`version_mismatch` 显式报错，不静默降级 |
| G-6 | 版权：游戏本体随包分发 | 中 | profile 只声明路径与启动方式，不分发本体 |
| G-7 | 「多」被理解成「什么都能玩」 | 中 | 账本只报实测深度；未验证一律 `untested` |

## 15. 宿主适配面：DSH / Codex / Claude Code / pi 各要什么

> 目标平台已定为四家。本节回答「PENS 主要适配哪些核心 agent 能力」。以下矩阵中，标注 **实测** 的项来自本机命令输出（2026-11-11），其余为文档级判断。

### 15.1 先分清两个适配面

| 面 | 方向 | 内容 | 本文档位置 |
| --- | --- | --- | --- |
| **入向（host→PENS）** | 宿主怎么调 PENS、能调多深 | 工具/命令调用、会话标识、文件、指令注入、审批、事件 | 本节 |
| **出向（PENS→应用）** | PENS 怎么驱动外部应用 | 六族适配器 + 每应用 profile | §4、§9 |

入向决定了**包长什么样**，出向决定了**能玩什么**。两者不能混：入向做厚（每个宿主深度集成）就会回到 N×M；出向做薄（只有一种应用）就失去价值。

### 15.2 四宿主能力矩阵（本机实测版本）

| 能力 | DSH | Codex CLI `0.167.0` | Claude Code `2.1.216` | pi `0.80.7` |
| --- | --- | --- | --- | --- |
| 工具调用 | ✅ 插件注册工具 | ✅ 内置 + 自定义 | ✅ 内置 + 自定义 | ✅ `read/bash/edit/write` + 扩展工具 |
| **MCP 客户端** | ✅ `packages/mcp/mcp-client`（**实测**） | ✅ `codex mcp add/list/login`（**实测**，含 OAuth） | ✅ `claude mcp add`（**实测**，stdio + HTTP） | ❌ **无内置**；靠扩展 `pi-mcp-extension` / `@earendil-works/pi-mcp`（npm 实测存在） |
| 指令注入 | ✅ `AGENTS.md` + skills | ✅ `AGENTS.md` | ✅ `CLAUDE.md` + skills + hooks | ✅ `AGENTS.md` **和** `CLAUDE.md` + skills + prompt templates |
| 会话标识 | ✅ session | ✅ session / resume | ✅ session / `--resume` | ✅ `--session-id` / `--continue` / `--fork` |
| 长作业/进度 | ✅ `packages/jobs`（**实测**） | ⚠ 后台 exec + 轮询 | ⚠ hooks 事件 | ⚠ `--mode rpc` 流 |
| 审批/权限 | ✅ policy/approval | ✅ approval modes + sandbox | ✅ permissions（allow/deny）+ `PreToolUse` hook | ⚠ `--approve` 信任 + `--tools/--exclude-tools` |
| 定时/唤醒 | ✅ jobs / schedule | ❌ 靠外部 cron | ❌ 靠外部 cron | ❌ 靠外部 cron |
| 工具裁剪 | ✅ | ✅ | ✅ | ✅ `--tools/--exclude-tools/--no-builtin-tools` |
| 结构化输出 | ✅ | ✅ | ✅ | ✅ `--mode json` / `rpc` |

三条实测结论：

1. **四家都读 `AGENTS.md` 家族**（pi 甚至同时读 `AGENTS.md` 与 `CLAUDE.md`）。所以「怎么用 PENS」这件事，**一份文档就能喂四家**，不需要四份。
2. **MCP 是 3/4 原生，不是 4/4**。pi 需要装一个扩展；但 pi 有 `bash` 工具——所以 **CLI 入口能覆盖 4/4，零扩展**。
3. **只有 DSH 自带调度**。另外三家都靠外部 cron，所以「持续玩」必须由宿主轮次驱动，或由外部 cron 起一次 headless 回合（与 D-019「不假设主动推送」一致）。

### 15.3 适配优先级：5 必需 + 3 加分

| 优先级 | 能力 | 为什么是它 | 落地形态 |
| --- | --- | --- | --- |
| **P0-1** | 工具或命令调用 | 唯一真正必需的入口 | MCP tool / shell 命令 |
| **P0-2** | 会话标识 | 租约、审计、续局都挂它 | `session_id` 透传 |
| **P0-3** | 文件与制品通道 | 存档、渲染图、回放必须落地 | 路径 + sha256 |
| **P0-4** | 指令注入 | 让宿主知道「什么时候用、怎么用」 | 一份 `AGENTS.md` 片段 + 一个 `SKILL.md` |
| **P0-5** | 结构化错误与退出码 | 宿主能据此降级，而不是瞎猜 | 6 类错误码 + 非 0 退出 |
| P1-1 | MCP 客户端 | 省掉 shell 转义与输出解析 | MCP server（stdio/HTTP） |
| P1-2 | 进度/事件 | 长作业的体验与取消 | job + 进度通知 |
| P1-3 | 工具裁剪 | 控制 token 税（§4.6 实测 8.9k/轮） | 从 4 个工具 + schema 资源起步，天然便宜 |
| P2 | 审批钩子 / 调度 / 并发 | 可后置，不做不影响首验 | 见 §8.2 权限四级 |

### 15.4 由此得到的四条架构决定

1. **双入口，不三入口**：MCP server（3 家原生）+ CLI（4 家通用）；不为任何一家写专用 SDK。
   - 包结构：`pens`（核心） + `pens-mcp`（薄 server，stdio/HTTP） + `pens` CLI（同一套动作，`--json` 输出）。
2. **一份文档**：`AGENTS.md` 片段（30 行：什么时候用、四条命令）+ `SKILL.md`（怎么用、game profile 怎么读）。Codex 读 AGENTS.md，Claude 读 CLAUDE.md（可软链/复制），pi 两个都读，DSH 读 AGENTS.md + skills。
3. **PENS 必须是用户域常驻服务，不能是宿主的子进程**：
   - Codex 有沙箱（禁网/禁进程树）、Claude Code 有权限门、pi 有 `--approve` 信任门——把 Blender/游戏起在宿主的进程树里必然被拦；
   - 形态：用户登录后常驻的本地服务（`127.0.0.1:<port>` 或命名管道），宿主侧只装一个薄 client（stdio↔HTTP 桥）或直接跑 CLI。
4. **治理自持 + 宿主复核**（defense in depth）：租约、`action_class` 权限、审计在 PENS 内部判定；宿主的 approval 只作第二道闸。理由：四家的审批语义不可通约（Codex 是模式、Claude 是 allow/deny 列表、pi 是信任位、DSH 是 policy），把判定放在宿主侧等于写四套逻辑。

### 15.5 能力探测与降级（接入前必做）

每个宿主 × 每项能力，只允许三种值：`已验证` / `不支持` / `未测`。**首验前必须实测的最小集**：

```text
pens_catalog                 → 能否拿到结构化 JSON（退出码 + stdout 可解析）
pens_attach + observe        → 是否能在同一会话内连续调用（不是一次就断）
pens_act 长作业              → 超时/取消后宿主是否知道（错误码能否透传）
文件制品                     → 宿主能否读到 PENS 给的路径（沙箱边界）
指令注入                     → 宿主是否真的读了 AGENTS.md/SKILL（行为可观察）
```

任一为「未测」时，文档与账本里必须写成未测，不得写成支持（D-019 的口径）。

### 15.6 明确不适配的四件事

| 不接 | 理由 |
| --- | --- |
| 宿主的记忆 / 人格 / 上下文装配 | 那就是第二套主体（D-004）；PENS 只回状态 |
| 宿主的任务调度语义 | 三家没有，一家有；标准化即绑定 DSH |
| 宿主的审批 UI | 只提供 `action_class` 标记，UI 归宿主 |
| 宿主的提示词格式 | 只给文档，不给模板：四家的注入机制不同，硬塞会反噬 |

### 15.7 组织形态：服务是唯一实现，插件只是壳

四种候选接法的对比（「以 plugins 接入各家」是其中一种）：

| 形态 | 适配成本 | 宿主耦合 | 能力面 | 跨宿主 | 沙箱内可跑 | 升级影响 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **全插件**（每家一个插件） | **N×M**（4 份实现） | 高（绑宿主版本与语言） | 最宽（tool+skill+UI+hook） | 差 | 受限 | 宿主升级即坏 | 不可行：Codex / Claude Code 没有任意插件体系 |
| **全 MCP** | 1 份 server | 低 | 窄（tool/resource/prompt，无 hook/UI） | 好 | 受沙箱限制 | 协议稳定 | 不够：pi 无原生 MCP；且 GUI 进程起不来 |
| **全 CLI** | 1 份 CLI | 最低 | 窄（一次一进程） | **最好（4/4）** | 是 | 无 | 作为**逃生门**，不作主路 |
| **服务 + 双接线**（推荐） | 1 份内核 + 4 个薄壳 | 低 | 中（MCP 面 + md 面） | 好 | 服务在用户域 | 内核升级不影响接线 | **推荐** |

**三层组织**：

```text
① 实现层（唯一）        pens-core（总线：catalog/lease/observe/act/events/permission/job）
   ─ 用户域常驻，127.0.0.1:<port> 或命名管道；宿主看不见它的内部

② 接线层（每宿主 ≤1 个薄壳，几十–几百行）
   DSH          → MCP 条目（或插件壳：注册 4 个 tool + 一个 skill）
   Codex        → `codex mcp add pens http://…/mcp` + AGENTS.md 片段
   Claude Code  → `claude mcp add pens …` + CLAUDE.md 片段（+ 可选 PreToolUse hook）
   pi           → `pi install <pens-extension>`（或纯 CLI，零安装）
   任意其他宿主 → `pens … --json`（CLI 逃生门）

③ 文档层（一份，四家共用）
   AGENTS.fragment.md（30 行：何时用、四条命令） + SKILL.md（怎么用、profile 怎么读）
```

**三条组织原则**：

1. **插件是发行形态，不是实现形态**。DSH 插件与 pi 扩展都只是「把同一个 core 的 4 个工具和一份 skill 注册进去」的壳；壳里不许有业务逻辑。这样宿主升级最多改壳，不会变成四个 fork。
2. **安装 ≠ 接线**（D-006 的落地）：`pens install` 装的是 PENS 自己；`codex mcp add …` 只是把一个指针写进宿主配置。删掉宿主配置不影响 PENS，反之亦然。
3. **文档是公共资产，代码不是**：四家的工具面必须是同一套术语与同一份 schema 说明；任何「Codex 专用说法」「Claude 专用入口」都会立刻造成体验分叉。

**仓库布局（PENS 自己的组织）**：

```text
pens/
  packages/core/            # 总线：会话/租约/作业/权限/错误码（无宿主依赖）
  packages/adapters/{libretro,cdp,mod,uia,pixel,protocol}/   # 六族
  packages/mcp-server/      # 薄：core → MCP（stdio + HTTP）
  packages/cli/             # 薄：core → 命令行（--json）
  packages/host-dsh/        # 可选壳：DSH 插件包装（内部起 core，不重写实现）
  packages/host-pi/         # 可选壳：pi extension 包装
  profiles/                 # 每应用一份声明（数据，非代码）
  docs/{AGENTS.fragment.md,SKILL.md}
```

**分发**：先 npm（`npx pens up` 即可起服务）；不做单文件二进制，直到出现「宿主环境没有 Node」的实测需求。**不做**：四合一安装器、per-host fork。

## 16. 桌面壳：外挂式，Electron 优先

> 2026-11-11 用户明确要求：**要有桌面版（Electron 或 Tauri），而且要做成「外挂 APP」的样式**。这一条覆盖本文档 §10 里「不做桌面壳」的旧范围结论（PENS 台账 D-005 本来就写着「简单主面板是产品方向」，所以这是回到产品方向，不是新增需求）。

### 16.1 「外挂式」的三个含义，一个壳全包

| 含义 | 具体要求 | 壳里的对应件 |
| --- | --- | --- |
| **不在宿主里** | 不依赖任何 agent 宿主；宿主全关掉它也在 | 托盘常驻 + 独立进程 + 只连 pens-core |
| **贴在别的应用上** | 能浮在 Blender/游戏窗口之上，半透明、不挡操作 | 无边框透明置顶窗 + 点击穿透 + 吸附 |
| **随手挂起** | 全局热键唤起、开机自启、看得到 agent 在干什么 | 全局快捷键 + 托盘菜单 + 状态灯 |

一句话：**它是挂在系统边上的一件「外挂装备」，不是某个 agent 的一扇窗。**

### 16.2 Electron vs Tauri：按 PENS 的真实负载判

| 判据 | Electron | Tauri | 权重 |
| --- | --- | --- | --- |
| 帧流预览（30–60fps） | ✅ `getUserMedia` / `WebCodecs` / MediaStream，成熟 | ⚠ 需 Rust 接 Windows Graphics Capture + 编码 + IPC 传帧 | **高**（HUD 的核心是看画面） |
| 置顶 + 透明 + 点击穿透 | ✅ `alwaysOnTop('screen-saver')` + `transparent` + `setIgnoreMouseEvents` | ✅ 支持，但边界情况多 | 高 |
| 全局热键 / 托盘 | ✅ 内置 | ✅ 插件 | 中 |
| 跟随目标窗口 | ⚠ 需 native 钩子 | ⚠ 同样需 native | 中（v2 才要） |
| 安装包体积 / 内存 | ❌ ~100MB / 150–300MB | ✅ ~8MB / 40–80MB | 中 |
| 与既有代码/经验 | ✅ 我们仓库已有 Electron 壳参照（淋雨家、DSH 桌面壳） | ❌ 无 | 中 |
| 屏幕捕获的跨平台一致性 | ✅ | ⚠ 各平台要各写 | 中 |

**结论：v1 用 Electron**。理由只有一句：**HUD 的本质是「实时看画面 + 叠加 + 能穿透」，这条链路 Electron 现成，Tauri 要自己造 3–5 倍工作量**。体积/内存是可接受的代价——它是个常驻小工具，不是编辑器。

**切 Tauri 的触发条件**（写清楚，避免拍脑袋）：实测安装包 > 120MB **或** 常驻内存 > 250MB 且用户抱怨；或需要更省电的长时间 HUD。届时切换成本很低——壳只是 core 的客户端，UI 与协议层分开，换壳不换 core。

### 16.3 三种呈现形态（"外挂"不等于"缩小版面板"）

| 形态 | 信息密度 | 放什么 | 不放什么 |
| --- | --- | --- | --- |
| **托盘（默认）** | 1 个图标 | 在跑几个应用、是否有等待授权、右键菜单 | 任何状态细节 |
| **悬浮 HUD** | 一屏 2–3 行 + 一张缩略帧 | 当前 app + 谁在操作 + 最近 3 个动作 + 「暂停/接管」按钮 + 热键提示 | 配置、日志全文、profile |
| **管理面（完整窗）** | 多页 | 应用列表与深度等级、租约、作业队列、权限账本、制品浏览、profile 编辑 | agent 的记忆/人格（红线） |

**产品红线（承接「无记忆、无人格」）**：壳只显示**世界状态 + 谁在动 + 能不能停**，不显示 agent 在想什么、记得什么。否则壳就变成了第二个记忆/人格的展示面。

### 16.4 壳在架构里的位置

```text
        ┌──────────── 桌面壳（Electron）────────────┐
        │ 托盘 / HUD / 管理面                        │
        │ 只做三件事：显示状态、转发人的意图、显示产物 │
        └───────────────┬───────────────────────────┘
                        │ 本地 HTTP（与 MCP/CLI 同一条路）
                        ▼
                  pens-core（唯一事实）
```

- 壳是 **core 的第三个客户端**（和 MCP 壳、CLI 同一个 schema），不持有游戏状态、不直接起应用；
- **人的授权从这里发生**（`save` / `network` 这类 `action_class` 的批准），这正好落在 PENS 台账 D-009 的「授权、凭据引用与审计」上——生成者是人，不是宿主；
- 壳崩了不影响 core 与任何 agent；core 崩了壳显示「离线」，不假装在线。

### 16.5 技术要点（哪些是坑）

1. **置顶层级**：要盖住全屏游戏，用 `screen-saver` 层级；普通 `alwaysOnTop` 会被全屏独占盖掉。
2. **点击穿透**：HUD 默认穿透（`setIgnoreMouseEvents(true, { forward: true })`），只有鼠标悬停在按钮区才临时可点——否则用户点不到下面的游戏。
3. **跟随窗口（v2 再做）**：贴住目标窗口需要 WinEventHook（移动/最小化/切前台），v1 只做「自由悬浮 + 吸边」，避免一开始就写 native 模块。
4. **多显示器与 DPI**：坐标、缩略帧、吸附边都要按显示器分别算。
5. **性能预算**：HUD 预览帧率默认 10fps（够看），展开时 30fps；截图/编码不在壳里做，**由 core 提供 `observe(region/frame)`**，壳只负责显示——否则壳会变成第二个像素采集器。
6. **合规**：叠加层在联网竞技游戏里可能被判违规——**联网时自动隐藏 HUD**（可在设置里只为单机启用）。

### 16.6 分期调整（壳进入路线）

| 期 | 内容 | 验收 |
| --- | --- | --- |
| **M0** | 内核 + 双接线（无壳） | 两宿主各玩 10 分钟（原验收不变） |
| **M1** | 壳只读：托盘 + HUD（看画面、看动作、看作业） | 打开 Blender 渲染，HUD 能实时显示进度与产物；点击穿透可用 |
| **M2** | 壳可授权 + 管理面（租约/权限账本/制品） | 一次 `save` 类动作经人批准才执行；拒绝后可回滚 |
| **M3** | 跟随窗口 + 多应用 + 六族铺开 | 吸附跟随、多实例、D0–D3 账本可读 |

壳不进 M0 的理由：**能力先于外观**。没有稳定的 core 与 4 工具，壳只能演示假数据；但壳一旦进入 M1，它就是 PENS 的产品面——用户看到的是这个外挂，MCP/CLI 是给 agent 的后门。

### 16.7 前后端分离：三个客户端，一个 API

「前端只负责页面管理，后端负责生命周期与电脑控制」这个切法是对的，但要按**所有权**切，不按「前后端」切。

```text
        agent 宿主（MCP）   脚本 / 无 MCP 宿主（CLI）     人（GUI）
              │                     │                      │
              └──────────┬──────────┴──────────────────────┘
                         ▼  唯一 API：HTTP/JSON + 事件流（WS/SSE）
                 ┌───────────────────────────────────────┐
                 │  pens-core：唯一事实与唯一的手和眼      │
                 │  控制面（catalog/lease/act/observe）    │
                 │  治理面（权限/审计/凭据引用）           │
                 │  应用面（六族适配器/进程生命周期）      │
                 │  采集面（屏幕/帧缓冲/结构化状态）       │
                 └───────────────────────────────────────┘
                         ▲
        SPA（同一份，后端托管）＋ 桌面壳（只做窗口能力）
```

**分界原则**：任何需要「跨重启、跨客户端、跨宿主」保持一致的东西，必须在后端；只在一次会话里、只影响一个人看法的东西，放前端。

| 必须后端（不可协商） | 可以在前端 |
| --- | --- |
| 进程启停 / 崩溃恢复（生命周期） | 页面路由、布局、HUD 位置与大小 |
| 输入合成、屏幕采集（**唯一的手和眼**） | 按钮 → 调 API（发起意图） |
| 租约与并发裁决（唯一裁决者） | 展示产物（图片、日志流、进度） |
| 权限判定与审计账本（唯一账本） | 本地偏好（主题、快捷键、语言） |
| 作业与超时（唯一时钟） | 二次确认的交互流程 |
| 凭据引用（不落前端） | — |

由此得到三个客户端，共用同一 API（**写进代码的硬约束：GUI 不得拥有 MCP/CLI 没有的能力**）：

| 客户端 | 谁用 | 形态 |
| --- | --- | --- |
| `pens-mcp` | agent 宿主 | stdio/HTTP 的薄 server |
| `pens` CLI | 脚本、无 MCP 的宿主、调试 | 子命令 + `--json` |
| **SPA + 桌面壳** | 人 | 一份前端，浏览器与壳共用 |

**前端形态的最省做法**：后端内置静态托管，前端是一份 SPA；桌面壳（Electron/Tauri）只是
`loadURL('http://127.0.0.1:<port>/')` + 窗口能力（透明/置顶/穿透/热键/托盘）。**壳里业务代码为零**，
所以「浏览器打开」与「桌面壳打开」是同一个 UI，壳可随时替换、UI 迭代不用重打包。

**一致性与安全**：

- 一致性：前端**不缓存世界状态**，只缓存视图偏好；重连时先拉快照再按 `cursor` 订阅（snapshot + cursor，与 MemPalace/工作台同一套模式）；前端禁止自行推断「应用已停止」，一切以后端事件为准。
- 安全：后端只绑 `127.0.0.1`；启动生成一次性 token 写入 `.pens/token`，MCP 壳/CLI/SPA 都从注入处拿；拒绝外网来源（防 DNS rebinding），写类动作（`save`/`settings`/`network`）必须人确认，且**判定在后端**，前端只是按钮。

**分期**：M1 先只出 SPA（浏览器开），验 UI 与 HUD 的交互逻辑；壳在 M1 后半段接入，只补窗口能力。这样前端风险与壳风险解耦。

### 16.8 core 的进程生命周期：必须存在 ≠ 必须手动启动

前后端分离的直接后果：**多了一个必须活着的进程**。这是真实成本，解决方案不是去掉它，而是让它**自举**。

**四条启动路径，用户永远不用记「先起服务」**：

| 路径 | 谁触发 | 做法 | 失败时 |
| --- | --- | --- | --- |
| CLI 自举 | 任何 `pens …` 命令 | 先读 `core.json` 探活；连不上就 `spawn(detached)` 一个再连 | 打印 `core_unavailable` 与日志路径 |
| MCP 自举 | `pens-mcp` 被宿主 spawn | 同上（MCP 壳启动时不假设 core 在） | 返回 MCP error，宿主可见 |
| 壳自举 | 桌面壳启动 | 同上；壳是第一个客户端 | 壳显示「离线」并提供「启动 core」按钮 |
| 登录自启 | 安装时可选 | 托盘常驻（开机拉一次） | 无（用户可手动 `pens up`） |

**单实例与端口**（避免「起了两个 core 抢同一个游戏」）：

```text
%LOCALAPPDATA%\pens\
  core.json   { pid, port, token, version, started_at, uptime }   # ACL 仅本人可读
  core.lock   # 排他文件锁：并发启动时只有一个胜出，其余等待并读 core.json
  logs\core-<date>.log
```

- 端口用 `0`（内核分配）写入 `core.json`，**不固定 7788**，减少冲突；
- `token` 每次启动随机生成，写进 `core.json`；MCP/CLI/SPA 都从那里取（SPA 通过壳注入或同源 cookie）；
- 客户端请求带 `X-Pens-Version`，与 `core.json.version` 不符时：提示升级，不静默混用。

**退不退出的判断（重要）**：**有没有托盘决定是否常驻**。壳在跑 → 常驻；只有 CLI/agent 在跑 → 空闲 N 分钟后自杀（`--idle-exit 15m`），下次谁用谁再 ensure 拉起。这样「多一个进程」的代价被压到「正在用的时候才多一个」。

**两种形态同一个包**：`pens-core` 既可作常驻服务，也可被 CLI 以库方式内嵌（`--in-proc`）用于测试与单客户端场景。但**生产多客户端必须走独立进程**——因为租约、输入、采集只能是单点。

**不做**：leader election（谁先起谁当主）。多客户端下仍要选主，等于再写一套一致性逻辑，收益为零。

## 17. 实现语言与工具链

> 一句话原则：**语言的边界是进程，不是模块。** core 定协议（JSON），适配器按族选语言、各跑各的进程；任何 FFI 都不许进 core。

### 17.1 候选对比（按 PENS 的真实负载打分）

PENS 的负载特征：本地 HTTP/WS、进程管理、状态机、**大量异构胶水**（模拟器 C ABI、CDP、UIA/COM、内存读写、截图输入）；不是 CPU 密集。

| 候选 | 生态贴合 | 开发速度 | 分发 | 性能 | 我们最熟 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **TypeScript（Node）** | CDP/Playwright 与 Mineflayer 都是第一；FFI 有 koffi；MCP 官方 SDK | 快 | 好（npx / 随 Electron） | 够（IO bound） | ✅ | **主选** |
| Rust | libretro/系统调用最强；CDP 生态弱、无 Mineflayer | 慢 | 最好（单二进制） | 过强 | 一般 | 热路径备用 |
| Go（台账 D-010 的原提案） | 胶水生态最弱（UIA 要手写 COM、CDP/Mineflayer 无成熟库） | 中 | 好 | 好 | 一般 | **不建议做 core** |
| Python | 模拟器 ctypes / pywinauto / mss 都最省 | 最快 | 差（打包、杀软误报） | 弱 | 一般 | 适配器备用 |
| 混合（推荐形态） | — | 快 | 中 | 够 | ✅ | **采用** |

**关键判断**：Go 的优势是「单二进制 + 并发」，但 PENS 的瓶颈在「接得上什么」，不在「跑得多快」；把 Go 放 core，等于让最弱的胶水生态承担最重的胶水活，而 Rust 的收益（性能）在这个负载上换不回来。

### 17.2 结论：一个主语言 + 进程级例外

| 组件 | 语言 | 理由 |
| --- | --- | --- |
| `pens-core` | **TypeScript** | 状态机 + 本地 HTTP/WS + 进程管理；与壳/SPA/CLI 同一 toolchain |
| `pens-mcp` / `pens` CLI | **TypeScript** | MCP 官方 SDK 是 TS；CLI 与 core 共享 zod schema |
| SPA（前端） | **TypeScript** | 与 core 共享同一份 schema 类型，零手写接口 |
| 桌面壳 | **Electron（TS）** | §16 已定 |
| 适配器 · 模拟器族 | **TS（koffi FFI）** → 不行则 **Python 子进程** | v1 先不引入第二个运行时；koffi 若在 libretro 回调上不稳，下沉 Python |
| 适配器 · CDP 浏览器族 | **TS（playwright-core，不下载浏览器）** | 生态第一 |
| 适配器 · 协议族（Minecraft 等） | **TS（mineflayer/prismarine）** | 生态唯一 |
| 适配器 · UIA / 像素族 | **TS（koffi + nut.js）** → 不行则 **Python（pywinauto/mss）** | 先用最少的运行时，踩坑再下沉 |
| 适配器 · Mod 族 | **游戏生态**（C# / Java） | 插件必须活在游戏进程里，与 core 语言无关 |

「进程级例外」的含义：**允许一个适配器用别的语言，但必须作为独立子进程，通过 JSON-RPC over stdio 与 core 说话**。core 永远不加载外来代码。

### 17.3 单一 schema，四端共用

```text
zod schema（一份）
  ├→ JSON Schema → MCP tools 定义
  ├→ HTTP API 请求/响应校验
  ├→ CLI 参数（--app/--action 的枚举）
  ├→ profile.yaml 校验（§9）
  ├→ SPA 的 TS 类型（生成，不手写）
  └→ 文档片段（工具表自动生成）
```

这条决定了一个隐性成本：**四端手写接口是 PENS 最容易腐化的地方**（字段名漂移、错误码不一致）。zod 单一来源是唯一可持续的做法。

### 17.4 工具链与分发

| 项 | 选择 |
| --- | --- |
| 运行时 | Node 22 LTS（与本仓 `^22.19` 一致） |
| HTTP / WS | Hono（轻）+ `ws` |
| 构建 | tsup / esbuild；CLI 走 `bin` + node |
| 打包 | 先 npx；需要单文件时用 bun compile 或 node SEA |
| Python 侧（如启用） | uv 管理 + 首版要求 Py 3.11+；不急着 PyInstaller |
| 测试 | node --test（与仓库一致）；适配器各自 mock 一个假应用 |

### 17.5 何时改语言（写清触发条件，避免拍脑袋）

| 信号 | 动作 |
| --- | --- |
| koffi 在 libretro 内存回调上不稳 / 崩溃 | 该族下沉 Python 子进程（不改 core） |
| 帧转发（30fps × 1080p）吃满 CPU | 帧管道单独用 Rust 写（core 仍 TS） |
| 用户机器没有 Node | 出 bun compile 单文件（claude/codex 都是这么发的） |
| 需要 UIA 高频操作 | Python 子进程（pywinauto 成熟度远高于 JS 绑定） |

### 17.6 与台账 D-010 的关系

台账写的是「Go 做 PENS 核心服务 · TypeScript 做面板」是**提案**，并明确「不得把 PENS 必须用 Go 当成已签字约束」。本节结论不推翻它，而是给出依据后的新建议：**core 用 TS，Go 暂不进入**。同时保留台账 D-005 的「PEN 包语言中立」——一个 PEN 可以带 Python/JS/Go/C#/Rust 的 runner，只要边界在进程。
